# Go Concurrency

Четыре задания на конкурентное программирование в Go: запуск горутин, конвейер на каналах, остановка фоновой задачи и потокобезопасный generic LRU-кэш.

Учебный проект School 21, AP1-Go-T02. Каждое задание сохранено отдельным Go-модулем. Внешних зависимостей нет.

Требуется Go 1.25.4 или новее.

## Состав

| Каталог | Задача | Основные инструменты |
| --- | --- | --- |
| `task1` | Запуск N горутин, ожидание и сортировка результатов | `sync.WaitGroup`, `sort` |
| `task2` | Генератор чисел и последовательное возведение в квадрат | goroutines, read-only channels |
| `task3` | Асинхронный тикер с остановкой по сигналу | channels, `os/signal`, `time` |
| `task4` | LRU-кэш со значениями произвольного типа | generics, map, двусвязный список, mutex |

## Запуск

Команды выполняются из соответствующего каталога.

```sh
cd task1
go run . -n 5 -m 100
```

Пять горутин спят от 1 до 100 мс. После завершения результаты выводятся по убыванию времени сна. Каждая горутина записывает только свой элемент среза, чтение начинается после `Wait`.

```sh
cd task2
go run . -k 2 -n 5
```

Результат: `4`, `9`, `16`, `25`, по одному числу на строку. Первый этап отправляет числа в канал, второй считает квадраты. Каждый этап закрывает свой выходной канал. Значения используют `int`: большие квадраты могут переполнить его диапазон.

```sh
cd task3
go run . -k 1
```

Тикер выводит номер тика и прошедшее время. `Ctrl+C` останавливает программу; также обрабатывается `SIGTERM` там, где он поддерживается ОС. Это учебный тикер на `time.Sleep`, а не точный планировщик: возможен временной дрейф.

`task4` — библиотечный пакет, у него нет команды запуска. Пример использования в другом Go-модуле после подключения пакета:

```go
cache := lrucache.New[string](2)
cache.Set("a", "first")
cache.Set("b", "second")
value, ok := cache.Get("a")
cache.Set("c", "third") // ключ b вытеснен
cache.Clear()
```

Ключи — строки, значения задаются параметром типа. `Get` и `Set` работают за O(1). Чтение также меняет порядок использования, поэтому `Get` берёт эксклюзивную блокировку. При ёмкости меньше или равной нулю кэш не сохраняет элементы.

## Проверки

В каждом из `task1`–`task4`:

```sh
go test ./...
go vet ./...
go build ./...
```

Проверить все модули из корня в PowerShell:

```powershell
foreach ($task in 'task1','task2','task3','task4') {
    Push-Location $task
    try {
        go test ./...
        if ($LASTEXITCODE -ne 0) { throw "Tests failed: $task" }
        go vet ./...
        if ($LASTEXITCODE -ne 0) { throw "Vet failed: $task" }
        go build ./...
        if ($LASTEXITCODE -ne 0) { throw "Build failed: $task" }
    } finally { Pop-Location }
}
```

Для Bash:

```sh
for task in task1 task2 task3 task4; do
  (cd "$task" && go test ./... && go vet ./... && go build ./...) || exit 1
done
```

Из корня `go test ./...` не используется: здесь четыре независимых модуля, а не один общий.

В `task2` проверяется конвейер и граница диапазона `int`; в `task3` — выдача тика и остановка без получателя; в `task4` — вытеснение, обновление, промахи, очистка, нулевая ёмкость и конкурентный доступ. `task1` проверяется запуском, отдельных unit-тестов у него нет.

Дополнительно внутри модулей можно выполнить `go test -race ./...`. Для этого нужны CGO и C-компилятор. На использованном Windows-окружении race detector не запускался из-за отсутствия компилятора.
